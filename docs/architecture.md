# Architecture

How `asa-research-prototype` is put together: the entry points, then a file-by-file walkthrough.
The [README](../README.md) covers *how to run* the project; this document covers *what the pieces
are*. For *why* they are built this way, see [Design decisions](decisions.md).

**The agent architecture is only beginning.** The package holds one real module — `ASASession`,
which owns a connection to the (virtual) Furhat — plus the machinery that proves packaging,
tooling and environment work end to end. What follows therefore describes the *structure* the
remaining agent code will land in as much as the agent itself. See [Roadmap](roadmap.md).

Relative links below are written from the repository root.

---

## How the pieces fit

Three ways in, converging on one function:

```text
  uv run asa                  uv run python -m asa          from asa import ASASession
       │                              │                                 │
       ▼                              ▼                                 │
 .venv/bin/asa                 src/asa/__main__.py                      │
 generated wrapper:            raise SystemExit(main())                 │
 sys.exit(main())                     │                                 │
       │                              │                                 │
       └──────────────┬───────────────┘                                 │
                      ▼                                                 │
              src/asa/cli.py                                            │
              main(argv) -> None                                        │
              owns the event loop: asyncio.run(...)                     │
                      │                                                 │
                      ▼                                                 ▼
              src/asa/session.py  ◄──── re-exported by ────  src/asa/__init__.py
              ASASession — async, loop-agnostic            (the public API)
```

The notebook path on the right matters more than it looks. `ASASession` never calls
`asyncio.run()` itself, so the *caller* owns the event loop: `main()` starts one, while a notebook
already has one running and simply awaits the session. A class that called `asyncio.run()`
internally would work from the CLI and raise `RuntimeError` in every notebook.

The two command-line paths are not redundant. The console script is generated by uv from
`[project.scripts]` and only exists if the package genuinely built and installed, so running it
tests the whole packaging chain. `python -m asa` skips all of that and tests only that the
package imports and its `__main__` shim works.

## Why the imports resolve

There is no `conftest.py`, no `sys.path` manipulation and no `pythonpath` setting anywhere. They
are not needed, because `uv sync` **installs this project into `.venv` in editable mode**:

```text
.venv/lib/python3.12/site-packages/
├── asa_research_prototype.pth              -> points at <repo>/src
└── asa_research_prototype-0.1.0.dist-info/
    └── direct_url.json                     -> {"dir_info": {"editable": true}}
```

The `.pth` file puts `src/` on `sys.path` for that interpreter, so `import asa` resolves from any
working directory. Because it points at the source tree rather than a copy, edits to `src/asa/`
take effect immediately — there is no re-sync step after changing code.

This is the single most consequential structural choice in the project, and it is what
distinguishes it from the sibling `dev-conv-agent`, which is deliberately not packaged and
resolves `import lib.*` by putting the repo root on the path instead.

### `src/asa/__init__.py` — the public API

Defines what `import asa` gives you: `ASASession`, `FurhatUnreachable` and `__version__`. Callers
write `from asa import ASASession` without knowing which module it lives in, so a later refactor
that moves the class but keeps the re-export won't break them.

Note the import direction. `__init__.py` imports *from* `asa.session`, never `from asa` — the
package cannot import a name it has not finished defining, and trying raises `ImportError:
cannot import name ... from partially initialized module`. Modules *inside* the package follow the
same rule for the same reason: `cli.py` imports `from asa.session import ASASession`, not
`from asa import ...`, so it does not depend on `__init__.py` having completed.

`__version__` is read at import time with `importlib.metadata.version("asa-research-prototype")`
rather than hardcoded, so `pyproject.toml` remains the single source of truth. Note this reads the
*distribution* name, not the import name.

### `src/asa/session.py` — the interaction session

`ASASession` owns a websocket connection to the Furhat for the life of one session. Construction
is cheap and does no I/O — a constructor cannot `await` — so the connection is opened in
`start()` and closed in `stop()`, with `__aenter__`/`__aexit__` wrapping the pair. The realtime
client provides no async context manager of its own, so without this a session that raised
mid-conversation would leak its websocket.

Connection failures are re-raised as `FurhatUnreachable`. The transport produces two different
exceptions for what is one problem to a caller — `ConnectionRefusedError` when nothing is
listening, `websockets` `InvalidMessage` when something that is not a Furhat holds the port — and
neither belongs in the vocabulary of code that just wants to talk to a robot.

### `src/asa/cli.py` — the command-line entry point

`main(argv=None)` parses arguments, configures logging, and runs one session. `argv` defaults to
`None` so argparse reads the real `sys.argv` for both entry points; passing an explicit list lets
a test drive `main()` without argparse picking up the *host* process's arguments, which is
otherwise unavoidable under pytest.

It carries no `if __name__ == "__main__":` guard: the console-script wrapper and `__main__.py`
each own their own entry path, so the guard would only ever fire for `python src/asa/cli.py`,
which is not a way anyone invokes a packaged project.

### `src/asa/_tools/` — private development utilities

Deliberately underscore-prefixed and never re-exported from `__init__.py`, so `from asa import ...`
cannot reach them. They ride along in the wheel, which costs nothing at import time and keeps them
importable from a notebook with no `sys.path` juggling. `custom_logging.setup_logging()` installs
a single stdout handler and raises the level on the `asa` and `__main__` logger trees, leaving
third-party libraries at the root `WARNING`.

### `src/asa/__main__.py` — the `-m` shim

`from asa.cli import main` then `raise SystemExit(main())`, unguarded — under `python -m asa` this
file *is* the main module by construction, so a `__name__` check would be redundant.

`SystemExit(...)` rather than a bare `main()` call makes the return value the process exit code,
matching what uv's generated console-script wrapper does (`sys.exit(main())`). Today `main()`
returns `None` and both exit 0; the point is that the two entry paths cannot diverge later, when
`main()` grows a failure path that returns non-zero.

### `tests/` — the pytest suite

| Test file | Covers |
| --------- | ------ |
| [`test_cli.py`](../tests/test_cli.py) | Argument parsing (defaults, explicit values, a rejected `--log`) and that an unreachable Furhat exits 1 rather than raising |
| [`test_lint.py`](../tests/test_lint.py) | Runs `ruff check .` across the repo as a test, so `uv run pytest` doubles as the lint gate |

`test_lint.py` invokes ruff as `sys.executable -m ruff` rather than a bare `ruff`, so it resolves
through the interpreter pytest is already running under. That makes it behave identically from
the terminal, from the VS Code Testing panel and in CI, none of which share a PATH. Note it lints
the whole repository, notebooks included, so a stray unsorted import in `notebooks/` fails the
test suite.

The unreachable-Furhat test stubs `ASASession` rather than pointing at a dead address. A test
that relied on nothing listening would silently invert its meaning the day a Furhat *is* running
locally, and would then connect to it and make the robot speak.
